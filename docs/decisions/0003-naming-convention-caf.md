# ADR-0003: CAF naming convention via `Azure/naming` module

- **Status**: Accepted
- **Date**: 2026-05-21
- **Decider**: Eyal
- **Supersedes**: —

## Context

Every Azure resource needs a name. Conventions drift fast if not pinned
early: one engineer types `vnet-hub-prod`, another types `hubVnetProd`,
a third writes `prod-vnet-hub`, and now policy assignments based on
prefix matching fail silently. Convention drift is a top-3 ESLZ failure
mode and the cheapest one to prevent.

Microsoft publishes the [CAF naming convention](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/azure-best-practices/resource-naming):

```
<resource-type-abbreviation>-<workload>-<env>-<region-abbr>-<instance>
```

Example: `vnet-hub-plat-weu-001`, `kv-reelhouse-dev-weu-001`.

The `Azure/naming/azurerm` Terraform module implements this convention
and handles ARM-imposed name constraints (storage account names must be
lowercase alphanumeric only; key vault names have a 24-character cap;
etc.).

## Decision

All Keystone resources are named per the CAF convention, generated by
the `Azure/naming/azurerm` Terraform module. Each layer declares one
naming module instance with that layer's `workload` and `env` inputs;
every resource name in that layer is sourced from the module's outputs.

## Consequences

**Positive:**

- Interview-defensible. The convention is published, named, and well-known.
- The module handles ARM constraint edge cases automatically (length caps,
  allowed character sets, lowercase requirements).
- Resource-type abbreviations are standardised — `vnet`, `pep`, `pdnsz`,
  `cae`, `ca`, `kv`, `st`, `psql`, etc. — so a fresh reader can read a
  resource ID and know the type without a lookup.

**Negative / trade-offs:**

- Some resources have ARM-level uniqueness requirements (storage account
  names are globally unique). The module appends a deterministic suffix
  to handle this; review per-layer to make sure it produces names that
  remain stable across re-plans.
- Module outputs change shape between major versions. Pin the module
  version explicitly (`source = "Azure/naming/azurerm" version = "X.Y.Z"`)
  and bump deliberately.

## Alternatives considered

- **Custom naming convention** — rejected. No published reference,
  harder to defend in an interview, and you would build the same
  ARM-constraint-handling logic the module already provides.
- **CAF convention without the module** — rejected. The module's
  constraint handling is the part most worth borrowing; reimplementing
  it by hand creates a maintenance tail with no learning upside.
- **No convention, ad-hoc names** — rejected on contact.
